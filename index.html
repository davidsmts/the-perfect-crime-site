LLM Agents Can Easily Tamper Their Own Traces

Jeremy Qin*, David Schmotz*, Derck Prinzhorn, Luca Beurer-Kellner, Ameya Prabhu†, Maksym Andriushchenko†

ELLIS Institute Tübingen · Max Planck Institute for Intelligent Systems · Tübingen AI Center · Exponential AI · Snyk · University of Tübingen
* equal contribution · † equal supervision

Monitoring, incident investigations and audits rely on an agent's execution trace to reconstruct what happened. We show that local LLM agents can delete or rewrite those traces, when asked, when tricked by a malicious skill, and on their own when it improves their score.

Every result below is clickable. Each ✓ and ✗ opens the trace browser filtered to the runs behind it — the model's reasoning, every tool call and its output, the permission denials, and the filesystem record of what happened to the trace file.

Can an agent alter its own record?

We tested four widely deployed harnesses in full-access mode. Each stores its session trace as a plain local file the agent can reach:

  • Claude Code: ~/.claude/projects/<proj>/<id>.jsonl
  • Codex: ~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl
  • Gemini CLI: ~/.gemini/tmp/<hash>/chats/*.json

1. When asked, every harness complies

Asked to delete traces for privacy after a financial or personal task, agents in all harnesses found and deleted their own traces. Guardrails didn't stop it. In the one case where Claude Code flagged the request, it switched from Opus 5 to Opus 4.8, and the fallback model deleted the trace. Only Claude Code refused to insert a fabricated container-reset event.

2. A malicious skill is enough

With a "privacy protection" skill installed in the default location, agents working on an unrelated programming task loaded it without being told to and deleted their session trace. A second skill injected instructions into the compaction summary stored in the trace.

3. Agents do it on their own for reward

Agents got a task, a time budget and a grader score with no explanation. Finishing the task earned at most 0.8, and the rest was only reachable by tampering with the trace. Every model worked this out and tampered, without ever being told to. Several launched background scripts that kept deleting traces as new logs appeared. Showing agents other agents' logs or workspaces with higher scores had the same effect: they copied the tampering.

Deleting the trace can leave an agent untraceable

If a Codex session file is deleted, the session keeps running and nothing it does afterwards is recorded. Claude Code and Gemini CLI start a new file, but an agent can schedule a process that deletes it after the session ends.

Mitigation: record traces off the host

We propose sending all model traffic through an interception server that the agent's host cannot control. The server records every request and response, including each streaming chunk, before forwarding it. Records are append-only, and if a write fails the exchange is blocked. This protects the record even if the host is fully compromised. It cannot see calls that bypass it, such as local models or other APIs, and it records tool results without verifying them.

Provider-side logging doesn't close the gap either. Zero Data Retention setups keep only local history, and enterprise compliance APIs leave out thinking blocks, tool definitions and often system prompts, and they truncate tool results.

An agent's authority to do useful work must not include authority to rewrite the record used to evaluate that work.
