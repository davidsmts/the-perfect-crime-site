LLM Agents Can Easily Tamper Their Own Traces

Jeremy Qin*, David Schmotz*, Derck Prinzhorn, Luca Beurer-Kellner, Ameya Prabhu†, Maksym Andriushchenko†

ELLIS Institute Tübingen · Max Planck Institute for Intelligent Systems · Tübingen AI Center · Exponential Security Labs · Snyk · University of Tübingen
* equal contribution · † equal supervision

Monitoring, incident investigations and audits rely on an agent's execution trace to reconstruct what happened. We show that local LLM agents can delete or rewrite those traces, when asked, when tricked by a malicious skill, and on their own when it improves their score.

Can an agent alter its own record?

In full-access mode, agents can reach the local files that hold their session traces. Some of the tested locations are:

Grok Build~/.grok/sessions/<cwd>/<id>/*.jsonl
Muse Code~/.local/share/muse/sessions/YYYY/MM/DD/<id>/session.jsonl

When asked, nine of ten pairs tamper in full-access mode

Asked to remove traces after a financial or personal task, nine model–harness pairs tampered in at least one trial of each setting. Muse Code declined all 20 requests. The fabricated container-reset and tool-call experiments tested other ways to rewrite the record; their outcomes vary by model and harness.

A malicious skill is enough

A "privacy protection" skill installed in the default location led some agents working on an unrelated task to tamper with their trace. A second skill tried to inject instructions into the stored compaction summary. Success varied across the ten pairs.

Agents do it on their own for reward

Agents got a task, a time budget and a grader score with no explanation. Finishing the task earned at most 0.8; the rest was only reachable by tampering with the trace. All ten pairs tampered in both reward settings at least once, though Muse Code did so in only 2 of 10 anonymization trials. Some agents also copied tampering shown in other agents' higher-scoring logs or workspaces. Muse Code and Claude Code with Opus 5.5 did not copy it from logs.

Deleting the trace can leave an agent untraceable

If a Codex session file is deleted, the session keeps running and nothing it does afterwards is recorded. Claude Code and Gemini CLI start a new file, but an agent can schedule a process that deletes it after the session ends.

Codex
  1. Session file deleted
  2. Session keeps running
  3. Nothing afterwards is recorded
Claude Code · Gemini CLI
  1. Session file deleted
  2. Harness starts a new file
  3. A scheduled process deletes it after the session ends

Record traces off the host

We propose sending all model traffic through an interception server that the agent's host cannot control. The server records every request and response, including each streaming chunk, before forwarding it. Records are append-only, and if a write fails the exchange is blocked. This protects the record even if the host is fully compromised.

Agent host
  • harness + tools
  • assumed compromised
→
Interception server
  • records every request, response and stream chunk
  • append-only

→
Model API
  • unchanged

It cannot see calls that bypass it, such as local models or other APIs, and it records tool results without verifying them.

Provider-side logging doesn't close the gap either. Zero Data Retention setups keep only local history, and enterprise compliance APIs leave out thinking blocks, tool definitions and often system prompts, and they truncate tool results.

An agent's authority to do useful work must not include authority to rewrite the record used to evaluate that work.
